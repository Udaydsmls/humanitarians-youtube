# CARRY-OUT — GATE C

Written before any other narration. Every beat exists to make this sentence survivable.

## The line

> **Multiply Claude's coordinates by original-over-sent, per axis — that
> inverse ratio is what turns a smaller image's pixels back into your real
> screen's pixels.**

## The wrong guess it defeats

That Claude's click is simply wrong — a guess, a miss, a flaw in the model —
when it's actually a units problem: Claude's coordinates are correct for the
image it was shown, which is not the same size as the screen you're clicking
on.

## The secondhand test

*If someone repeats only this sentence in a meeting next week, is it still true?*

Yes — it compresses the one distinction that matters (the model's coordinate
space vs. the screen's coordinate space, and the one ratio that maps between
them) without smuggling in a claim about which vision API resized the image
or by how much.

## What it deliberately does not say

- Not which resize algorithm or interpolation method the API uses internally
  — the source doesn't specify one, so neither does this reel.
- Not a general claim about all computer-use frameworks — the source's one
  input, one worked ratio, generalizes to any resize but is only demonstrated
  on it.
- Not a verdict on whether sending a downscaled screenshot is the "right"
  design choice for a vision API — that's a design judgment (Teardown's
  lane), not Plain's.
