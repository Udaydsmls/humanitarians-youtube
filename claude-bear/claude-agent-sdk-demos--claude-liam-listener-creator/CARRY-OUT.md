# CARRY-OUT — GATE C

Written before any other narration. Every beat exists to make this sentence survivable.

## The line

> **A listener isn't a watcher hovering over your inbox — it's a file
> naming one condition, and it fires on exactly that condition, every
> time, and stays silent on anything that only feels the same.**

## The wrong guess it defeats

That a Skill's "listener" must be a live process, actively scanning your
inbox the moment you ask for it. It isn't: open the `listener-creator`
folder and there's no watcher running — just a `SKILL.md` file (about nine
kilobytes, plain text) and a `templates` folder beside it. Two files.
Claude reads the file's Steps section and works through it top to bottom,
writing the condition you asked for into a definition; nothing in the
folder watches anything on its own.

## The secondhand test

*If someone repeats only this sentence in a meeting next week, is it still true?*

Yes — it compresses the one distinction that matters (a listener is a
written condition, not a judgment call) without overstating what a defined
listener can catch beyond its own file.

## What it deliberately does not say

- Not a claim that listeners can never be broadened — only that *this*
  listener fires on only what its own condition currently names.
- Not a verdict on whether that design is good or limiting (Teardown
  territory) — Plain states the mechanism and the boundary, and stops.
- Not that every Skill has exactly this shape — `listener-creator` is the
  worked example; the anatomy (SKILL.md + supporting files, Steps section)
  is the pattern this reel demonstrates, not a universal spec.
